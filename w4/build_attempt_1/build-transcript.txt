## 4. Questions I would have asked the spec author

1. EC-7 detection responsibility. Should the LLM return all 3 dates in
   one response, or should the orchestrator detect multi-shift after
   parse? My implementation does the latter via regex, which feels brittle.
2. FM-2 retry scope. Does "retry once after 5s" cover only timeouts, or
   also JSON schema failures? Schema failures often won't fix themselves
   on retry.
3. FM-3 visibility. When the agent falls back to default shift times,
   does the resulting record get a flagged_ambiguities entry, just an
   audit row, or both?
4. EC-4 duplicate handling. Spec says "add DUPLICATE_SUSPECTED; do not
   auto-cancel; route to coordinator review." Does "route to coordinator
   review" mean set status to CLARIFICATION_NEEDED, or keep PENDING_MATCH
   with the flag visible? I chose CLARIFICATION_NEEDED.
5. Multi-shift + duplicate. What happens if shift #2 of a 3-shift block
   duplicates an existing record? My code flags only that one shift and
   lets the others go to PENDING_MATCH — but the spec doesn't say.
6. Idempotency key. EC-7 says (servicenow_ticket_id, ticket_sequence_num).
   Does the FIRST poll cycle need to be atomic across all 3 sequence
   rows (transactional)? Mine inserts them one-by-one with autocommit.
7. HIPAA / PHI in source_text. Spec says don't log source_text in
   plaintext app logs. My audit_log table doesn't store it, but I print
   log lines via Python logging that include ticket_id but not
   source_text. That feels right but isn't explicitly confirmed.
8. CRNA / NP / specialty-only requests. What confidence applies if the
   source text says only "need an NP" with no unit type? Unit_type=UNKNOWN
   drops the unit-type component to 0, capping overall at 0.64 ->
   clarification. Intended?

## 5. Places where I had to choose between two interpretations

- Postgres vs SQLite. Spec was Postgres. I switched to SQLite stdlib
  because Postgres wasn't installable in the build window. Alternative:
  punt the whole DB layer.
- hospital_exists semantics in mock mode. I treat the _default fallback
  as "hospital not found" for EC-6 purposes (only explicit keys count
  as known hospitals). Alternative: treat any successful default lookup
  as "hospital known" — would break EC-6.
- EC-7 split point. I split multi-shift inside the orchestrator using a
  regex after the LLM returned a single date. Alternative: have the
  FakeLLMClient return all 3 dates and have the orchestrator just iterate.
- FM-3 ambiguity flag. I added an INSUFFICIENT_INFORMATION flag when
  profile was missing and status was PENDING_MATCH. Alternative: just
  log the warning and leave the flag list alone (closer to the literal
  spec text).
- Duplicate ambiguity sets status to CLARIFICATION_NEEDED. Alternative:
  keep status PENDING_MATCH and rely on the flag visibility.
- EC-2 unit_type=GENERAL for "step-down". I hardcoded this in the canned
  FakeLLM response per the spec's example. Alternative: GENERAL with
  inference_confidence of 0.5 might better reflect reality.
- _build_llm_client() defaults to Fake when no API key. Alternative:
  hard-fail at startup. I chose Fake to make local dev frictionless,
  since spec says "set MEDFLEX_API_BASE_URL=mock for local testing"
  already.
- Multi-shift ticket_sequence_num reuses ticket_id. Spec mentions
  (servicenow_ticket_id, ticket_sequence_num) as the idempotency key.
  I implemented this but no UNIQUE constraint enforces it at the DB
  level — only application-side check. Alternative: add a UNIQUE index
  in the SQLite schema.
